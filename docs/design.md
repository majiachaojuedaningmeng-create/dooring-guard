# 设计说明

这份文档记录取舍，而不是复述代码。看完应该能回答：为什么这么判、误差在哪、下一步往哪走。

## 1. 问题被简化成了什么

原始问题：**在开门之前，判断推门这个动作会不会撞到人。**

它其实有两半：

- 后方有没有东西正在接近（感知）
- 我打算什么时候开门（意图）

本项目只做前半段，并且把后半段固定成一个假设：**车门将在「现在」打开**。
所以输出的语义不是「以后会撞」，而是「如果此刻推门，会撞」。

这个简化让整个系统变成一个纯感知问题，可以离线跑视频验证，不需要真的接车门信号。
代价是它给不出「3 秒后开门是否安全」这类预测 —— 那需要轨迹外推，当前版本没做。

## 2. 为什么不用端到端模型

三条理由，按重要性排序：

1. **没有数据。** 训练一个「门开瞬间是否碰撞」的模型，需要大量带标注的真实门碰场景，
   这类数据既不公开、也不好采（涉及真实事故）。没有数据的情况下上模型，只能上预训练检测器，
   那本质上还是「检测 + 规则」，只是把规则藏进了后处理里。
2. **要能解释。** 一个只会输出 0.87 的黑盒，在「为什么刚才没报警」这个问题面前毫无还手之力。
   而这个项目最需要回答的恰恰是这个问题。
3. **要能搬到板子上。** MOG2 + 轮廓在 RDK X5 的 CPU 上就够跑，不占 BPU。
   真上 YOLO 的话，10 TOPS 只能跑轻量模型，还得走模型转换，属于下一阶段的事。

所以这里的默认路线是：**用最土的方法把判据跑通，把精度问题留给数据和标定**。

## 3. 距离代理：用包围盒高度代替真距离

单目相机下，物体成像高度与距离的关系是：

```text
h = f · H / Z          →     Z = f · H / h
```

其中 `f` 是焦距、`H` 是物体真实高度、`Z` 是距离。也就是说 **Z 与 1/h 成正比**。

而项目里用的是对 `h` 做线性归一化：

```text
d = (h - h_far) / (h_near - h_far)
```

这是在 `h` 上线性、在 `Z` 上非线性。严格来说，`TTC = Z / v` 和代码里的 `TTC = (1-d)/v`
不是同一个量，后者在远处会明显高估时间。

**为什么还是这么写：** 因为我们只在「快撞上」的区间里要它准。车身宽度 1.8 m 的车，
在 20 m 外成像高度可能只有 40 px，在 3 m 内有 300 px —— 近处 `h` 的分辨率天然更高，
恰好是决策最需要的区间。远处的误差被 `CAUTION` 这个宽档吸收掉了，不影响结论。

**已知的正确做法**（没实现，列在 README 的 roadmap 里）：改用 `1/h` 做距离代理，
或者用已知尺寸的参照物（车牌宽 440 mm、轮胎直径）反推真实 `Z`，再算真实 TTC。

## 4. 状态机与滞回

三个状态，四个阈值，两组：

| 迁移 | 进入条件（严格） | 退出条件（宽松） |
|---|---|---|
| SAFE → CAUTION | `d ≥ 0.55` 或 `TTC ≤ 4.0s` | `d < 0.40` 且 `TTC > 6.0s` |
| CAUTION → DANGER | `d ≥ 0.92` 或 `TTC ≤ 1.5s` | `d < 0.78` 且 `TTC > 2.5s` |

必须做成滞回，是因为单帧的 `h` 有抖动（检测框本身在跳），
直接用单一阈值会在边界上疯狂翻转 —— 实测如果不加滞回，6 秒的测试视频能报出 5 次
`CAUTION`，其中 4 次是假的。加了之后是 1 次。

同一类问题还有两个：

- **冷启动保护**：轨迹出现后前 6 帧不算风险。第一帧的 `Δt` 极小，`v = Δd/Δt` 会被放大成
  一个荒谬的速度，`TTC` 直接算出 2 秒多，于是视频一开头就误报一次 `DANGER`。
- **速度上限**：`v` 截断到 3.0（距离比例/秒）。否则两个目标合并、框突然变大时，
  同样会炸出一个假的 `TTC`。

## 5. 检测层踩过的坑

**碎片合并。** 目标被拆成两块是常态：车轮和车身之间、贴地的阴影、被遮挡后的断口。
不合并的话跟踪器会当成两个目标，凭空多出一条假轨迹（实测里就出现过 `t=4.13` 那条
`distance_ratio=0.043` 的幽灵轨迹）。所以 `detect.py` 里加了一个 `_merge`：
横向重叠超过 50%、纵向间隙小于较矮者高度的一半，就并成一个框。

**轨迹按时间戳记，不按帧号。** 因为真实视频的帧率并不稳定，掉帧时按帧号算 `Δt` 会把速度算错。

**IoU 阈值取 0.15，偏低。** 目标快速变大时（30 fps 下每帧高度能涨 15 px），
相邻帧的 IoU 会掉得很快，阈值高了就会频繁断轨、换 ID。

## 6. 迁移到 RDK X5 的路径

当前代码是纯 CPU 的 OpenCV，搬到板子上要动三处：

1. **解码**：`cv2.VideoCapture` 换成板子的硬件解码通路（GStreamer / V4L2），否则 1080p 解码就吃满 CPU。
2. **检测**：MOG2 换成 YOLO 一类的小模型，`.pt` 走官方工具链转成 `.bin` 跑 BPU。
   10 TOPS 下 YOLO11n 单线程约 120 FPS（INT8 / 640×640），足够留出余量。
3. **报警**：接 GPIO 驱动蜂鸣器或车内屏，把 `DANGER` 变成能听见的东西。

风险分级这层不用改 —— 它只依赖「框的高度」，与前端用什么检测器无关。这是刻意留的接口。

## 7. 还没做的评测

要让这东西从 demo 变成能说的东西，缺的是：

- 一段真实路边视频，人工标注「门开时刻」与「是否碰撞」
- 在这个集合上报 **误报率**（不该报却报了）和 **漏报率**（该报没报），
  而不是只贴一张好看的关键帧
- 做一次 `--near` / `--far` 的敏感度扫描，看阈值挪 10% 结论会不会翻

现在的合成测试视频只能证明 pipeline 连通，不能证明它准。这一点在 README 里也写清楚了。
